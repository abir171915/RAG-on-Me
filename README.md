# Ask Abir: A RAG System About My Professional Background

**Live demo: [abir171-ask-abir.hf.space](https://abir171-ask-abir.hf.space)**

A retrieval-augmented generation (RAG) system that answers questions about my work: my CV, my MSc thesis, my published research paper, and my GitHub projects. Ask it *"Has Abir worked on medical imaging?"* and it retrieves the relevant passages from my documents, then answers using only those sources and cites where each fact came from. If the documents don't contain the answer, it says so instead of guessing.

I built it from scratch as a modular, installable package and took it all the way to production: a measured retrieval pipeline, a FastAPI service with a web UI, a Docker image, and a public deployment.

> The free tier sleeps after a period of inactivity. If the demo shows *"Preparing Space"*, give it about a minute to start.

## How it works

```
                    ┌──────────────── INGEST (run once, when data changes) ────────────────┐
 data_dir/          │  load PDFs + GitHub READMEs  →  chunk  →  embed  →  store in ChromaDB │
 ├─ pdf_file/       │  (PyMuPDF, GitLoader)          (1000c)   (MiniLM)   (persisted)       │
 └─ github/repos.txt└───────────────────────────────────────────────────────────────────────┘

                    ┌──────────────────────── QUERY (every question) ───────────────────────┐
 Browser / client   │  rewrite question  →  retrieve top 5  →  LLM answers from context     │
   POST /ask   ───► │  (Groq LLM)           (cosine search)     (grounded prompt, cites     │
                    │                                            sources, says "I don't     │
                    │                                            know" when unsupported)    │
                    └───────────────────────────────────────────────────────────────────────┘
```

| Stage | Implementation | Module |
|---|---|---|
| Load | PDFs via `PyMuPDFLoader` (one Document per page); GitHub repos via `GitLoader` (README + requirements only) | `data_loader.py`, `loading_git.py` |
| Chunk | `RecursiveCharacterTextSplitter`, 1000 chars, 200 overlap | `chunking.py` |
| Embed | `sentence-transformers/all-MiniLM-L6-v2` (384-dim, runs locally) | `embedding.py` |
| Store | ChromaDB, persisted to disk, cosine distance, deterministic IDs + upsert | `vector_store.py` |
| Rewrite | LLM rewrites the question into a more specific search query | `query_rewriter.py` |
| Retrieve | Embed the query, top-k similarity search, merge and deduplicate | `search.py` |
| Generate | Groq `openai/gpt-oss-20b`, temperature 0, grounded prompt, returns answer + sources | `generator.py` |
| Serve | FastAPI: web UI at `/`, `POST /ask`, `GET /health` | `api.py`, `static/index.html` |
| Configure | `pydantic-settings`: every setting overridable by environment variable | `config.py` |
| Evaluate | Hit rate and recall@5 on a labelled question set | `evaluate.py`, `eval_set.py` |

## Results

Retrieval is evaluated on 10 labelled questions. Each one lists the source(s) that *should* be retrieved. They include specific facts, skills, paraphrased questions and list questions.

| Configuration | Hit rate@5 | Mean recall@5 |
|---|---|---|
| Baseline (original question only) | 0.80 | 0.72 |
| Multi-query rewriting with a fixed vocabulary list | 0.80 | 0.63 |
| **Single anchored query rewrite (current)** | **1.00** | **0.85** |

- **Hit rate** is the share of questions where at least one correct source appears in the top 5.
- **Recall** is the fraction of all expected sources that were retrieved. This is what matters for list questions like *"what deep learning projects…"*.

## Design decisions and what I learned

### Retrieval

**Local embeddings, hosted LLM.** The documents include my CV and thesis. Embedding them locally keeps that text on my machine, and only the few retrieved chunks are sent to the LLM. MiniLM is also free and fast for a corpus of this size.

**Only READMEs and requirements from GitHub, not code.** Questions like *"what did Abir build?"* are answered by prose, not by source code, which embeds poorly against natural-language questions. `requirements.txt` is included because it reliably lists the tech stack.

**Query rewriting: the first version made results worse, and the evaluation showed it.** My first rewriter produced three queries per question, steered by a list of technical terms from my documents. On a single test question it looked like a clear win. On the full evaluation set it *lowered* recall from 0.72 to 0.63: it fixed one question and broke three. Looking at the queries showed why. The rewriter replaced the user's own words with terms from the list, so *"What was the MSc thesis about?"* became *"CNN ResNet image classification"*. That query matched a different project very strongly and pushed the thesis out of the results. The current rewriter **anchors on the user's key terms** and only adds closely related terms around them, which took recall to 0.85.

**Raw similarity scores from different queries are not comparable.** Merging results from several queries by raw cosine similarity lets a confidently *wrong* query dominate. This is why the current design uses a single rewritten query, and why rank-based fusion (RRF) is on the roadmap before multi-query retrieval comes back.

### Engineering

**Ingest and query are separate.** `ingest` builds the vector store once. The app and API only embed the incoming question, and the API loads the model once at startup (about 20 s), so each request takes about 1–2 s.

**Deterministic chunk IDs with `upsert`.** With random IDs, every re-ingest would duplicate the whole store. Stable IDs make re-running safe.

**OS-independent metadata.** The store was first built on Windows and stored full file paths. Inside a Linux container, `Path(...).name` doesn't treat `\` as a separator, so the API returned full Windows paths as sources. Each chunk now stores a plain `source_name` at ingest time, so the data reads the same on any OS.

**Configuration from the environment.** Every setting lives in one `Settings` class and can be overridden by an environment variable, so the same code runs on a laptop, in Docker and on Hugging Face without edits. Only the entry points read the settings. The building blocks (`Retriever`, `VectorStore`, …) take plain parameters, which keeps them easy to test and reuse.

**Treat LLM output as untrusted input.** The rewriter's output is checked, capped, and falls back to the original question if it is empty. The web UI sanitises the generated answer before rendering it, because the model's input includes document text that could contain markup.

**Fail loudly, not silently.** Several bugs during development were invisible: an encoding issue that made a loader skip a file, an LLM that returned empty output and triggered a silent fallback, a typo in an expected source name. The code now logs a warning when a fallback fires, the evaluation refuses to run if an expected source doesn't exist in the store, and invalid configuration fails at startup.

### Docker and deployment

- **CPU-only PyTorch.** The default Linux wheel bundles about 2 GB of CUDA libraries that a CPU server never uses.
- **Pinned versions** via `constraints.txt`, so the container runs the same ChromaDB version that wrote the vector store.
- **Layers ordered by how often they change:** dependencies and the embedding model come before the code. A code-only rebuild went from **238 s to 13 s**.
- **Only the built vector store goes into the image**, not the source documents. The API key is passed at runtime and is never baked into the image.
- **Runs as a non-root user**, with a `HEALTHCHECK` on `/health`.
- **Deployed on Hugging Face Spaces** from a separate, thin deployment repo that installs this package **pinned to a GitHub commit**, so a new version only goes live deliberately. The free tier runs Spaces on ZeroGPU hardware, which expects a Gradio app. The deployment works around that by registering a placeholder GPU function and running ZeroGPU's startup step itself before serving the FastAPI app.

## Running it locally

**Requirements:** Python 3.10+ (developed on 3.12), and a free [Groq API key](https://console.groq.com).

```powershell
# 1. Create and activate a virtual environment
python -m venv myrag
.\myrag\Scripts\Activate.ps1

# 2. Install the package and its dependencies (editable mode)
pip install -e .

# 3. Add your API key to a .env file in the project root
Set-Content -Path .env -Value "GROQ_API_KEY=your_key_here" -Encoding ascii
```

Write `.env` lines as `KEY=value` with no spaces and no quotes. Docker's `--env-file` reads the file literally and rejects anything else. In Windows PowerShell 5.1, don't create it with `echo ... > .env`, which writes UTF-16.

**Documents.** Put PDFs in `data_dir/pdf_file/`, and list GitHub repos in `data_dir/github/repos.txt`, one URL per line. An optional branch can follow the URL; the default is `main`.

Run from the project root:

```powershell
python -m rag_on_me.ingest                  # build the vector store (first run clones the repos)
python -m rag_on_me.app                     # ask questions in the terminal; 'q' to quit
python -m rag_on_me.evaluate                # measure retrieval quality
python -m uvicorn rag_on_me.api:app --reload   # web UI at http://127.0.0.1:8000
```

Use `python -m uvicorn` rather than a bare `uvicorn`, so the server runs with the virtual environment's Python.

Re-run `ingest` whenever the documents change. If you **remove** a document, delete `data_dir/vector_store/` first: upsert adds and updates entries but never deletes them.

### Configuration

Every setting can be overridden with an environment variable (or a line in `.env`):

| Variable | Default | Purpose |
|---|---|---|
| `GROQ_API_KEY` | (none) | Groq API key (required for answers) |
| `DATA_DIR` | `<project>/data_dir` | Location of documents and the vector store |
| `COLLECTION_NAME` | `abir_profile` | ChromaDB collection |
| `EMBEDDING_MODEL` | `all-MiniLM-L6-v2` | Sentence-transformers model |
| `LLM_MODEL` | `openai/gpt-oss-20b` | Model that writes answers |
| `REWRITER_MODEL` | `openai/gpt-oss-20b` | Model that rewrites queries |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | `1000` / `200` | Chunking (applies at ingest) |
| `TOP_K` | `5` | Chunks retrieved per question |

### Docker

```powershell
docker build -t rag-on-me .
docker run --rm --name rag-on-me --env-file .env -p 8000:8000 rag-on-me
```

Then open http://127.0.0.1:8000. The image contains the built vector store, so run `ingest` before building.

## Known limitations

- **List questions are the weak spot.** Questions whose answer spans several projects (e.g. *"medical imaging work"*, recall 0.33) often retrieve several chunks from one project instead of one from each.
- **The data is imbalanced.** The MSc thesis and the research paper make up about 65% of all chunks, so they get more chances to match any question.
- **About 19% of chunks exceed MiniLM's 256-token limit** and are truncated during embedding.
- **The evaluation set is small** (10 questions, single run), so differences of one question can move the scores noticeably.
- **Only retrieval is evaluated.** Answer quality (faithfulness, correct "I don't know") is not yet measured.
- **The image is large (about 2.8 GB)**, mostly PyTorch.
- **The public demo shares one Groq free-tier key**, so heavy use can hit rate limits. The ZeroGPU workaround relies on internals of Hugging Face's `spaces` library and may need updating if that library changes.
